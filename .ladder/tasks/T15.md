Checked: `git diff 504d6ea` (the commit before T13 started) for src, tests, docs, deploy, README.md, skein.example.toml and agents; PLAN.md C8; the mcp 1.30 handlers skein wraps (authorize, token, register, revoke, client_auth). Issues (fix these), ranked:

1. src/skein/oauth.py:296 (`HashedSecretAuthenticator.authenticate_request`) with :869: `client_secret_basic` is advertised, but a token request that carries the client id only in the Basic header gets 401 `Missing client_id`. RFC 6749 §2.3.1 does not ask for `client_id` in the body when Basic is used, and the MCP TypeScript SDK's client prefers Basic when the client has a secret and the server lists it, sending no `client_id` in the body. This only touches clients with a secret, which is the pre-registered path C8 was added for (`skein oauth client add`). Reproduced in the smoke: authorize and consent fine, then `/token` with `Authorization: Basic <id:secret>` and no `client_id` field → 401. The existing test (tests/test_oauth.py:761-765) sends `client_id` in the body as well, so it passes. → Keep wrapping, don't fork: a small ASGI shim in front of the token and revoke handlers that reads the form body (already size-capped) and, when it has no `client_id` and the request has a Basic header, adds the client id from the header before the SDK handler reads it. The secret check stays where it is. Tests: code exchange and refresh with Basic and no `client_id` in the body → 200; a Basic id that differs from a body `client_id` → 401; wrong secret → 401.

2. src/skein/oauth.py:908 (the `RevocationHandler` mount, route at :941): `/revoke` only works when the form has a `client_secret` field. The SDK's `RevocationRequest` makes that field required, so a public client (registered with `none`, the usual MCP client) sending the RFC 7009 form (`token` + `client_id`) gets 400 `client_secret: Field required` and its tokens stay valid. A client with a secret using Basic gets the same 400. Reproduced for both; with `client_secret=""` added, the same public-client call returns 200 and ends the grant. README.md:172 ("A client can end its own grant by calling `/revoke`") and :145 ("at `/token` or `/revoke`, by basic or post") promise more than this. tests/test_oauth.py:587 only covers a client that posts its secret. → In the same shim, add an empty `client_secret` field on `/revoke` when the form has none (the authenticator has already run by the time the SDK validates the form, so a client that owes a secret is still refused). Tests: public client revoke with only `token` and `client_id` → 200, access and refresh dead; client with a secret revoking with Basic → 200; without any secret → 401.

3. agents/claude/README.md:26: still says `choose "No sign in" (skein does not do OAuth)`. That is wrong once `[oauth]` is on, and T14 flagged it without an owner. → Reword to "No sign in" for the fixed-token setup, and point to the README's OAuth sign-in section for connectors that only take OAuth. Line 16 can stay.

4. src/skein/oauth.py:812-823 (`_page`, the CSP): the consent hand-back is still not checked in a real browser, and the departure from the frozen C8 header text still has no ledger `decision` line. I drove the flow with httpx only, so this stays open. What is known: Chromium cancels a redirect that follows a form POST unless the target is listed in `form-action` (django-oauth-toolkit issue 1623 is the same symptom and the same fix; MDN describes browsers as inconsistent here), so listing the client's redirect origin is the right call. What is not covered: a client whose callback address itself redirects on to another origin or to an app scheme. As far as I know Chromium applies `form-action` to every hop after the POST, and later hops are not in the list. → Add the ledger decision line. During the redeploy check, do one sign-in in Chrome with DevTools open, before the user's retry. If the console shows "Refused to send form data … form-action", the fix that keeps `form-action 'self'` exactly as C8 has it: answer the approved POST with a 200 `no-store` page that hands back through `<meta http-equiv="refresh">` plus a visible Continue link, instead of a 303 (a meta refresh is not a form submission, so `form-action` does not apply to it).

Lows (same round if cheap, otherwise leave):

5. src/skein/oauth.py:933 (the `/register` route): a body that is not JSON, or a `client_name` with a lone surrogate (`"\ud800"`, fails at the insert after :420), returns 500 with a traceback on stderr. No secret or request text is in the traceback, and the server keeps running. → Catch both at the route and return 400 `invalid_client_metadata`.
6. src/skein/oauth.py:176 (`_loopback_any_port`): the any-port match ignores the fragment and userinfo, so `http://127.0.0.1:6000/cb#f` and `http://user:pw@127.0.0.1:6000/cb` are accepted for a client registered with `http://127.0.0.1:5000/cb`, although `check_redirect_uri` refuses both at registration. The redirect still only goes to loopback, so nothing leaks. Also, `http://[::1]:<other port>/cb` is refused because pydantic returns the host as `[::1]` and src/skein/service.py:59 lists `::1`. → Require no fragment and no userinfo on the requested URI, and strip the brackets before `is_loopback`.
7. README.md:135-136: redirect addresses "must be https, or http on localhost" leaves out private-use schemes (`com.example.app:/cb`), which are accepted; "registrations idle for more than a day" means registrations over a day old that hold no code or token (both from the T14 review, still open).

What the smoke confirmed:
- Migration: the v1 copy went to `user_version` 2 on the first `skein status`, with the four OAuth tables added and every members, meta, tasks and asks row identical before and after. Six processes opening one fresh v1 copy at the same moment all succeeded. Old fixed tokens, the point, the disabled member and the old task all work through the running server.
- Discovery as a client does it: 401 on `/skein/mcp` and `/skein/api/whoami` with `resource_metadata` → protected-resource metadata (resource `…/skein/mcp`, authorization server `…/skein`) → authorization-server metadata at the path-inserted root URL (issuer, the four endpoints under base, S256 only). The openid-configuration and base-appended copies return the same documents.
- Full flow, public registered client: register → authorize (302 to the consent page on public_url) → wrong token (400, counted, not echoed) → member token (303 to the registered redirect with code and state) → token → MCP initialize, tools/list, `tools/call skein_whoami` and REST whoami all return that member.
- Open redirect: ten redirect variants (other host, userinfo trick, `..`, added query, trailing slash, scheme change, `//host`, `javascript:`) all get 400 with no Location. An unknown client gets no redirect. Errors only go to a registered address. An extra `redirect_uri` in the consent POST is ignored. Deny goes to the registered address with `access_denied` and the state.
- PKCE: `plain`, a missing challenge, a malformed challenge, a wrong verifier and a missing verifier are all refused. `response_type=token` and a foreign `resource` are refused.
- Codes and tokens: a code is single use, bound to its client and redirect, and a replay ends the grant it produced. Refresh rotates and the old refresh token is refused. A refresh token is not a bearer, an access token is not a refresh token, and neither is accepted on the consent page. Another client cannot refresh or revoke someone else's token. An access token in `?token=` is refused while `url_tokens` is off.
- Consent page: CSP `default-src 'none'` with `frame-ancestors 'none'`, `X-Frame-Options: DENY`, `no-store`, `no-referrer` and `nosniff` on the form, the error form and the redirect; no cookie and no CORS header. A hostile client name and state are escaped, an unknown `req` is not reflected, a forged Host header is not reflected, and a 70 KB body gets 413. There is no session or cookie, so CSRF has nothing to ride on: the POST needs the unguessable `req` and the member token itself. A disabled member's token and an empty token count as misses, and the fifth miss ends the request.
- Client secrets: `oauth client add` prints the secret once; post and Basic (with `client_id` in the body) work; a wrong or missing secret gets 401, at refresh too; `client list` never shows it. The database holds no secret, code, token, verifier or member token in clear (58 values checked against every OAuth table and `members`). Trust on first use: http, a private scheme and a missing redirect are refused before the lock; the first approved https address locks the client; a second in-flight request to another address gets the conflict page and no code; `javascript:` is refused by the CLI.
- Revocation from the owner's side, against the running server: `member rotate` kills the member's access token, refresh token and an unused code, and leaves another member's tokens alone; `member disable` kills them for good (still dead after enable); `oauth client remove` kills that client's tokens. Revoke by a client works when a `client_secret` field is present (issue 2).
- Identity: 80 concurrent MCP and REST calls with two OAuth identities, no crossing. A member's OAuth token gets 403 on a point route and the point's gets 200.
- Logs: none of the 58 secrets appears in the audit log, server stdout or server stderr. No request lines are logged. The audit log has register, consent_ok, consent_failed, consent_denied, consent_conflict, token_issue, token_refresh, token_revoke, code_reuse, register_limited and the `*_failed` events, with ids, member names and status only.

Notes (not blocking):
- Registration is open and the consent page asks for a long-lived member token, so anyone can register an app with any name and send the owner a link to the real consent page. The page does say "An app calling itself …" and names where approving sends you, which is the right mitigation. If the only OAuth client a deployment needs is a pre-registered one, a config switch to turn dynamic registration off would remove that surface. That is a C8 change and needs a decision.
- The registration limit (src/skein/oauth.py:105) counts every POST, failed ones included, for the whole server: ten requests a minute from anyone hold off new registrations. Existing clients are unaffected.
- The registration response has no `Cache-Control: no-store`, and for the default auth method it carries a client secret. This comes from the SDK handler; the shim from issue 1 could add the header.
- Still open from T13, unchanged: `/authorize` is not rate limited and the 200 pending requests are shared by the whole server (:101, :466); an owner-added client without a redirect address sends error redirects to any https address until its first approved sign-in (documented in the README); a reused, already rotated refresh token is refused but does not end the grant, and the access token issued before a refresh stays valid until it expires.
